# マソ君の日常
## ～理想の自分育成型筋トレ日記～ 基本設計書

---

## 1. 設計方針

本アプリは、筋トレ記録と2Dキャラクター育成を組み合わせたWebアプリケーションとして設計する。

MVPでは、Next.js、Supabase、Vercel、GitHubを用いて、スマートフォン・PCのブラウザから利用できる構成とする。

クラウドDBにユーザーごとのトレーニング記録、種目、育成状態、設定情報を保存し、記録されたトレーニングボリュームを育成ポイントやエサとしてマソ君に反映させる。

---

## 1.1 MVP設計方針

- 主要画面は「ホーム画面」「記録画面」「トレーニング記録画面」「履歴分析画面」とする。
- 画面下部にボトムナビゲーションを配置する。
- ボトムナビゲーションから「ホーム画面」「記録画面」「履歴分析画面」へ遷移できるようにする。
- 記録画面には、カレンダー、追加ボタン、設定ボタンを設置する。
- カレンダーの日付、または追加ボタンから「トレーニング記録画面」へ遷移する。
- トレーニング記録画面では、部位別に種目を選択できるようにする。
- 未登録種目は、種目追加ボタンから新規登録できるようにする。
- 記録保存時に、種目ごとの換算パターンと、自重を使う種目ではその日の体重から、トータルボリュームを自動計算する（6章）。
- 有酸素（ウォーキング・ランニングなど）は未換算とし、時間（分）だけを記録する。ボリュームは0で、育成ポイントは付かない。
- トータルボリュームを育成ポイントに変換し、ポイントをエサ（5種類）に交換してマソ君に与えることで、成長に反映する。
- 保存済みの記録は、記録画面から編集・削除できる。育成ポイントは台帳（reward_ledger）で差分調整する。
- 記録・育成・名前の更新はDB関数（RPC）に限り、入力検証をクライアントとサーバーの両方で行う。

---

## 1.2 技術選定

| 分類 | 技術 | 役割 |
|---|---|---|
| フロントエンド | Next.js / React / TypeScript | 画面表示、画面遷移、UI制御 |
| UIデザイン | Tailwind CSS / shadcn/ui | スマホ向けUI、ボタン、モーダル、フォーム |
| 2Dマソ君表示 | PNG / SVG | レベルや状態に応じたキャラクター表示 |
| 2Dアニメーション | CSS Animation / Framer Motion | エサやり、レベルアップ、画面演出 |
| バックエンド | Next.js Server Actions / API Routes | 記録保存、計算処理、DB連携 |
| DB | Supabase PostgreSQL | 記録、種目、設定、育成状態の保存 |
| 認証 | Supabase Auth | ログイン、ユーザー管理 |
| 画像管理 | Supabase Storage | マソ君画像、将来的なスキン画像管理 |
| ホスティング | Vercel | Webアプリ公開 |
| ソース管理 | GitHub | コード管理、自動デプロイ連携 |
| BGM | Web Audio API / MP3 | トレーニング向けはブラウザ内で曲を生成、リラックス向けはMP3を再生 |
| テスト | Vitest / PGlite | 単体テスト、メモリ内PostgreSQLによる実DB検証 |

実装での違い（2026年10月時点）：

- UI部品は shadcn/ui を使わず、Tailwind CSS 4 とLucideで構成した。Framer Motion は使っていない。
- 記録保存・計算などのバックエンド処理は、Server Actions / API Routes ではなく、ブラウザからSupabaseのDB関数（RPC）を呼ぶ。サーバー側ではNext.js Proxyがセッションを更新し、未認証時にログインへ誘導する。
- マソ君の画像は `public/maso` のSVGで、Supabase Storage は使っていない。
- 接続情報がない場合は、データを `localStorage` に保存するローカルプレビューとして動く。クラウド用（`AppDataProvider`）とローカル用（`DemoDataProvider`）で、同じ操作と検証を持つ。

# 4. DBに格納するデータ種別を設計する

本アプリではSupabase PostgreSQLを利用する。  
ユーザーごとのトレーニング記録、種目、育成状態、設定情報を管理する。

---

## 4.0 方針

- 全テーブルでRLSを有効にし、ユーザーは自分の行だけを参照できる。
- 記録・育成ポイント・エサ・名前の書き込みはDB関数（RPC）に限る。テーブルへの直接のINSERT/UPDATEは許可しない。直接更新できるのは、設定（セット数・単位）と種目名だけである。
- RPCは `auth.uid()` を使い、呼び出し側が任意のユーザーIDを指定できない。再実行しても二重に処理されないよう、リクエストIDを使う。
- DBの変更は番号付きのマイグレーション（`supabase/migrations/`）で行う。

---

## 4.1 profiles

アカウントの表示名を管理する（`auth.users` と1対1。メールアドレスはSupabase Authが持つ）。

| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 更新日時 |

## 4.3 exercises

種目情報を管理する。標準種目（61種）は、登録時に全ユーザーへ作成する。

| カラム名 | 型 | 内容 |
|---|---|---|
| id | uuid | 種目ID |
| user_id | uuid | ユーザーID |
| name | text | 種目名（60文字以内） |
| body_part | text | 部位 |
| is_default | boolean | 標準種目かどうか |
| master_key | text | 標準種目のキー（追加種目はnull） |
| calculation_pattern | text | 換算パターン A / B / C / D |
| bw_ratio | numeric | 体重係数（0〜1） |
| is_isometric | boolean | 静的種目（秒数入力）かどうか |
| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 更新日時 |

部位は次の8つで、`body_part` には `chest / back / legs / shoulders / arms / abs / cardio / other` を保存する。

- 胸
- 背中
- 脚
- 肩
- 腕
- 腹
- 有酸素（未換算。時間のみ記録する）
- その他

種目の追加は `add_exercise` RPC を使い、換算パターンと係数はサーバー側が部位から決める。クライアントから換算パターンを指定することはできない（[換算ロジック仕様](換算ロジック仕様.md)）。同じユーザー・部位で、大文字小文字と前後の空白を除いた名前の重複は登録できない。

## 4.4 workout_logs

トレーニング記録を管理する。記録時の体重・係数から計算した値を保存するため、あとから係数を調整しても過去の記録は変わらない。

| カラム名 | 型 | 内容 |
|---|---|---|
| id | uuid | 記録ID |
| user_id | uuid | ユーザーID |
| exercise_id | uuid | 種目ID（同じユーザーの種目だけを指す複合外部キー） |
| client_request_id | uuid | 再実行対策のリクエストID |
| workout_date | date | トレーニング実施日 |
| weight_kg | numeric | 重量（kg。自重種目は追加重量。有酸素は0） |
| assist_kg | numeric | アシスト重量（kg。懸垂系のみ） |
| body_weight_kg | numeric | 計算に使った体重（kg。不要な種目はnull） |
| load_per_unit_kg | numeric | 1回（静的種目は1秒、有酸素は0）あたりの総負荷 |
| reps | integer | 回数（静的種目は秒数、有酸素は時間[分]） |
| sets | integer | セット数 |
| volume_kg | numeric | トータルボリューム（生成列） |
| memo | text | メモ（500文字以内） |
| deleted_at | timestamptz | 削除日時（論理削除。nullなら有効） |
| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 更新日時 |

計算式：

```text
volume_kg = load_per_unit_kg × reps × sets
育成ポイント = floor(volume_kg / 100)
```

1回あたりの総負荷（`load_per_unit_kg`）は、種目の換算パターンから決まる。ウエイトのみの種目（A）では重量そのもの、自重を使う種目（B〜D）では体重と係数も使う。有酸素は0である。詳細は [換算ロジック仕様](換算ロジック仕様.md) を参照する。

# 6. 公開後に追加した設計（2026年10月）

公開後の指摘（[要件定義書](要件定義書.md) 6章）への対応で追加した設計を、ここにまとめる。

## 6.1 総負荷の換算

種目ごとの換算パターンで、1回あたりの総負荷を決める。BWはその日の体重、ratioは種目の体重係数である。

| パターン | 総負荷 | 対象 |
|---|---|---|
| A | 重量 | 体が固定され、自重が上下しない種目（ベンチプレス等） |
| B | 重量 + BW × ratio | 体も持ち上げる下半身種目（スクワット等） |
| C | BW × ratio + 重量 | 自重の一部を負荷にする種目（プッシュアップ等） |
| D | BW × ratio + 重量 − アシスト | ぶら下がり・支持の種目（懸垂・ディップス等） |

- 静的種目（プランク等）は秒数で入力し、10秒を1レップとして換算する。
- 有酸素は未換算とする。時間（分）だけを記録し、ボリューム0で育成ポイントも付かない。判定は種目ではなく部位で行う。
- 体重は1日1件を保存し、入力がなければ記録日以前で最も新しい体重を使う。
- 記録には計算に使った体重と総負荷を保存する。係数を調整しても、過去の記録は変わらない。
- 標準種目と係数は `lib/data/exercise-master.ts`（SQLは `exercise_master()`）が正本で、単体テストが一致を確認する。

詳細は [換算ロジック仕様](換算ロジック仕様.md) に定める。計算は `lib/domain/load.ts`、`lib/domain/workout-load.ts`（TypeScript）と、`save_workout`・`compute_workout_values`（SQL）に同じ規則で持ち、一致を単体テストと実DB検証で確認する。

## 6.2 入力検証

クライアントの入力欄とサーバー（RPC）で、同じ上限を検証する。

| 項目 | 上限・規則 |
|---|---|
| 重量・アシスト | 500kg以内。ウエイトのみの種目（A）は0より大きい値 |
| 回数 | 200回（静的種目は600秒、有酸素は600分） |
| セット数 | 30以内 |
| 体重 | 20〜300kg |
| 1回の記録のボリューム | 50,000kg以内 |
| 日付 | 未来日は不可 |
| メモ | 500文字以内 |

入力欄でEnterキーを押しても保存しない。保存は「この記録を保存」ボタンだけで確定する。

## 6.3 報酬の差分調整（記録の編集・削除）

- 記録に付与済みの育成ポイントは、`reward_ledger` の `workout_reward` と `workout_adjustment` の合計である。
- 編集・削除では、目標値 `floor(volume_kg / 100)`（削除は0）と付与済みの合計の差を、調整行として台帳へ追加する。
- すでにエサへ交換して使ったポイントを戻して、所持ポイントが0を下回る場合は、0を下回らない範囲までしか戻さない。次の調整は台帳の合計（実際に付与された値）が基準になるため、下げて上げ直してもポイントを増やせない。
- 削除は論理削除（`deleted_at`）で、台帳の外部キーを保つ。
- 同じリクエストIDの再実行は、二重に適用しない。

## 6.4 名前の検証

マソ君の名前と表示名は、他のユーザーに見える可能性がある（将来のフレンド機能）ため、次を行う。

1. 正規化：ゼロ幅文字・ハングル埋め字・点字空白などの見えない文字を除去し、空白を詰め、Unicode正規化（NFC）する。見える文字が残らない名前は拒否する。
2. 禁止ワード判定：全角・半角、大文字小文字、カタカナ・ひらがな、記号の挿入、数字や記号による置換（`5h1t` など）を同一視して判定する。短い英単語は単語単位で判定し、普通の語の誤検出を減らす。
3. 同じ規則をTypeScript（`lib/domain/display-name.ts`、`name-filter.ts`）とSQL（`normalize_display_name`、`is_name_allowed`）に持ち、サーバー側でも拒否する。語彙（`lib/domain/name-filter-terms.json`）の一致は単体テストで確認する。
4. 新規登録時に使えない名前だった場合は、登録を失敗させず既定の名前にする。

## 6.5 エラー処理

通信断・ログイン切れ・入力不備・競合などを分類し、利用者が次の行動を分かるように案内する。方針と分類は [エラー処理方針](エラー処理方針.md) に定める。

## 6.6 BGM

- トレーニング向け4曲は、Web Audio APIでブラウザ内に生成する（音源ファイルなし）。曲のパターン生成、先読みスケジューラー、リミッターをかけた出力で構成する。
- リラックス5曲は、CC0の音源ファイルをMP3で再生する。
- 曲の選択・音量・再生状態はブラウザごとに保存し、アカウント間では同期しない。新規ユーザーの既定はトレーニング向けの曲とする。
- 自動再生が制限された場合は、画面の操作後に再生する。生成・再生に失敗した場合は再試行を案内する。
