# 「マソ君の日常」開発手引き

## 0. この手引きの目的

この手引きは、`基本設計書.md` と `要件定義書.md` を、実際に着手できる大きさの開発作業へ分解したものである。

対象はMVPとし、次の4画面を中心に実装する。

1. ホーム画面
2. 記録画面
3. トレーニング記録画面
4. 履歴分析画面

開発は「見た目だけを一気に作る」のではなく、各フェーズで動作確認できる小さな完成状態を積み重ねる。

---

## 1. 開発全体の進め方

### 1.1 推奨フェーズ

1. 仕様の未確定事項を決める
2. 開発環境とプロジェクト基盤を整える
3. 画面遷移と共通UIを作る
4. SupabaseプロジェクトとDBを作る
5. 認証とユーザー初期データ作成を実装する
6. トレーニング記録機能を実装する
7. 記録カレンダーと一覧を実装する
8. 育成ポイント・エサ・レベル機能を実装する
9. ホーム画面を完成させる
10. 履歴分析を実装する
11. 設定機能を実装する
12. テスト、セキュリティ確認、性能改善を行う
13. Vercelへ公開する

### 1.2 1機能ごとの基本サイクル

各機能は次の順で作る。

1. 受け入れ条件を書く
2. 必要なデータを確認する
3. UIの空状態、読込中、成功、失敗を決める
4. DBまたはServer Actionを実装する
5. UIを実装する
6. 正常系を手動確認する
7. 入力エラーや通信エラーを確認する
8. lint、型チェック、テスト、buildを実行する
9. 小さな単位でコミットする

## 2. 実装開始前に確定する仕様

設計書だけでは実装方法が一意に決まらないため、以下を先に決定する。

### 2.1 育成ポイント・エサの換算

最低限、次を数式として決める。

- ボリューム何kgで育成ポイント1になるか
- ボリューム何kgでエサ1になるか
- 1回の記録で付与できる上限
- 小数を切り捨て、切り上げ、四捨五入のどれにするか
- 自重種目や有酸素運動をどう計算するか

MVPの暫定例：

```text
volume = weight_kg × reps × sets
growth_point = floor(volume / 100)
earned_food = floor(volume / 500)
```

この値は仮置きであり、コードへ散在させず、1か所の定数または計算関数で管理する。

### 2.2 レベルアップ条件

決定項目：

- レベルごとの必要経験値
- レベル上限
- エサ1個あたりの経験値
- 一度のエサやりで使える数
- 余剰経験値を次レベルへ繰り越すか
- 複数レベルを一度に上げられるか
- レベルごとの画像

暫定例：

```text
必要経験値 = 100 × 現在レベル
エサ1個 = 10経験値
余剰経験値は繰り越す
```

### 2.3 記録編集・削除時の扱い

ここはデータ不整合が起きやすいため、実装前に必ず決める。

- 記録を編集した場合、育成ポイントとエサを差分調整するか
- 獲得済みのエサを使用した後に元記録を削除できるか
- 削除は物理削除か論理削除か
- 履歴分析に削除済み記録を含めるか

MVPでは、次のどちらかを選ぶ。

- 単純方式：保存後の記録は編集・削除不可
- 整合性重視方式：付与履歴を台帳化し、編集・削除時に差分取引を追加する

基本設計書には編集・削除状態があるため、後者が設計との整合性は高い。

### 2.4 重量単位

推奨方針：

- DBには常にkgで保存する
- lb入力時にkgへ変換して保存する
- 画面表示時にユーザー設定へ合わせて変換する
- 換算係数は `1 lb = 0.45359237 kg` とする
- DB上の元データと表示値の丸め規則を分離する

### 2.5 日付・タイムゾーン

- ユーザーが選ぶトレーニング日は `date` として保存する
- 作成・更新日時はタイムゾーン付き日時を使用する
- MVPの表示基準は日本時間に固定するか、ユーザーのブラウザ時間に合わせるか決める
- 日別・週別・月別集計の境界を決める
- 週の開始曜日を月曜または日曜のどちらかに統一する

### 2.6 名前変更の対象

要件には「マソ君またはユーザー名」と揺れがある。以下を分ける。

- ユーザー表示名：`users.display_name`
- キャラクター名：`maso_status.maso_name`

MVPで変更できる対象を明記する。

## 5. SupabaseとDB設計

### 5.1 認証ユーザーとプロフィールの分離

Supabase Authが認証ユーザーを管理するため、独自 `users` テーブルはプロフィール用として扱う。`auth.users` と同じIDを主キーにする。

推奨：

```text
profiles
- id uuid primary key references auth.users(id)
- display_name text
- created_at timestamptz
- updated_at timestamptz
```

基本設計書の `users.email` は重複管理になりやすい。MVPではAuth側のメールを参照し、プロフィール表へ複製しない方が単純である。

### 5.2 推奨テーブル

最低限：

- `profiles`
- `user_settings`
- `exercises`
- `workout_logs`
- `maso_status`
- `food_wallets` または `foods`
- `food_logs`
- `growth_logs`

編集・削除時の報酬整合性を保つ場合は追加する。

- `reward_transactions`

### 5.3 制約をDBで保証する

例：

- `default_sets > 0`
- `weight_kg >= 0`
- `reps > 0`
- `sets > 0`
- `volume_kg >= 0`
- `level >= 1`
- `experience >= 0`
- `food_point >= 0`
- `weight_unit in ('kg', 'lb')`
- `body_part` は定義済み値のみ
- 1ユーザーにつき設定1件
- 1ユーザーにつき育成状態1件
- 同一ユーザー内で種目名を重複させない

### 5.4 外部キーと削除規則

- ユーザー削除時にユーザーデータを削除するか、保持するか決める
- 種目に記録がある場合、種目を物理削除しない
- 種目には `is_archived` を設け、過去記録を壊さず非表示化できるようにする
- 記録削除は `deleted_at` を使う論理削除も検討する

### 5.5 RLS

すべてのユーザーデータ表でRLSを有効化する。

基本方針：

```text
SELECT: auth.uid() = user_id
INSERT: auth.uid() = user_id
UPDATE: auth.uid() = user_id
DELETE: auth.uid() = user_id
```

`profiles.id` のように主キー自体がユーザーIDなら `auth.uid() = id` とする。

RLSは「画面で他人のIDを送らない」だけでは代替できない。SQL Editorまたはテストから、別ユーザーのデータを読めないことを確認する。

### 5.6 インデックス

最低限検討する。

- `workout_logs(user_id, workout_date)`
- `workout_logs(user_id, exercise_id, workout_date)`
- `exercises(user_id, body_part)`
- `food_logs(user_id, created_at)`
- `growth_logs(user_id, created_at)`

### 5.7 初期データ

- 部位別のデフォルト種目をseedへ定義する
- 新規ユーザーが利用開始したとき、設定、育成状態、エサ残高を作る
- ユーザーごとにデフォルト種目を複製するか、共通種目として `user_id = null` にするか決める

### 5.8 DBフェーズの完了条件

- migrationだけで空のDBを再構築できる
- seedでデフォルト種目を投入できる
- 制約違反データを登録できない
- ユーザーAがユーザーBのデータを読めない
- 型定義をDBから生成できる

## 7. トレーニング記録機能

この機能を最初の業務機能として完成させる。育成と分析の元データになるためである。

### 7.1 入力項目

- 日付
- 部位
- 種目
- 重量
- 重量単位
- 回数
- セット数
- メモ
- トータルボリューム

### 7.2 入力画面の動作

1. URLの日付を初期値にする
2. ユーザー設定からデフォルトセット数と重量単位を読む
3. 部位を選ぶ
4. 選択部位の種目だけを表示する
5. 種目を選ぶ
6. 重量、回数、セット数を入力する
7. 入力変更ごとに表示用ボリュームを計算する
8. 保存時にサーバー側でも再計算する
9. 成功後、対象日の記録画面へ戻る

### 7.3 入力検証

- 日付が正しい
- 未来日の入力を許可するか決める
- 種目が現在ユーザーから利用可能
- 重量が0以上
- 回数が1以上
- セット数が1以上
- メモ文字数が上限以内
- NaN、Infinity、空文字を拒否
- 小数点以下の桁数を制限
- 極端に大きい値を拒否または警告

クライアント側検証は操作性のため、サーバー側検証は安全性のために両方行う。

### 7.4 ボリューム計算

計算ロジックはUIから分離し、単体テスト可能にする。

```text
volumeKg(weight, unit, reps, sets)
```

画面に表示された値を信用して保存せず、サーバー側で入力値から再計算する。

### 7.5 種目追加

必要項目：

- 種目名
- 部位

確認事項：

- 前後空白を除去
- 空文字を拒否
- 最大文字数
- 同じユーザー・同じ正規化名の重複を拒否
- 保存後に選択肢へ即時反映
- 追加した種目を自動選択する

### 7.6 保存処理

記録保存と報酬付与は、一方だけ成功しないよう原子的に扱う。推奨はSupabaseのDB関数を使い、次を1回の処理にする方法である。

1. 入力検証
2. ボリューム計算
3. `workout_logs` 追加
4. 報酬計算
5. エサ残高またはポイント更新
6. 報酬取引履歴追加
7. 結果返却

同じ保存要求が二重送信されても二重付与しない仕組みを検討する。保存中はボタンを無効化し、可能なら冪等性キーを用いる。

### 7.7 完了条件

- 部位で種目を絞り込める
- 新しい種目を追加できる
- 設定したセット数が初期表示される
- kgとlbの表示が設定に従う
- 入力中にボリュームが表示される
- DBに保存されたボリュームがサーバー計算値と一致する
- 二重クリックで二重記録されない
- 保存失敗時に入力内容が消えない

## 9. 育成機能

### 9.1 データ上の責務を分ける

- トレーニング保存：エサや育成ポイントを獲得する
- エサやり：保有エサを消費して経験値を得る
- レベル判定：経験値に応じてレベルを更新する
- 表示：現在レベルに応じた画像を選ぶ

### 9.2 エサやり処理

1. 使用数を受け取る
2. 1以上か検証する
3. 現在残高以上を使っていないか検証する
4. エサを減らす
5. 経験値を増やす
6. 必要経験値を超えた間、レベルアップ判定する
7. `food_logs` を追加する
8. レベルが変わったら `growth_logs` を追加する
9. 新しい状態を返す

残高確認と更新はDB側で同時に処理し、連打による残高のマイナスを防ぐ。

### 9.3 画像切り替え

- レベル帯と画像ファイルの対応表を定数またはDBで管理する
- 画像がないレベルでも代替画像を表示する
- `alt` には状態が分かる説明を付ける
- PNGを使う場合はサイズを最適化する
- 単純な動きはCSS Animationを優先する

### 9.4 完了条件

- エサがないときに実行できない
- エサ使用数だけ残高が減る
- 経験値が正しく増える
- 閾値到達時だけレベルが上がる
- 余剰経験値の扱いが仕様どおり
- 同時実行でも残高がマイナスにならない
- レベルに応じて画像が変わる
- 使用履歴と成長履歴が残る

- モーダル表示中は背後へフォーカスが移動しないようにする

### 10.3 エサやり演出

演出は保存成功後に行う。先にアニメーションだけ再生して失敗を隠さない。

状態例：

- 通常
- エサやり中
- 成功
- レベルアップ
- エラー

### 10.4 完了条件

- 最新状態を1回のまとまった取得で表示できる
- 経験値ゲージが0〜100%の範囲に収まる
- エサやり後、リロードなしで値が更新される
- レベルアップ時に画像と数値が更新される
- 名前変更が再読込後も保持される
- モーダルをキーボードでも操作できる

### 11.1 最初に作る分析

3. 月別トータルボリューム
4. 部位別合計
5. 種目別の重量またはボリューム推移

### 11.2 集計の設計

- 集計期間を明示する
- タイムゾーンと週開始日を統一する
- 削除済み記録を除外する
- DB側集計とクライアント側集計の責務を決める
- 大量データを全件ブラウザへ送らず、必要な粒度で集計する

MVP初期は記録量が少ないため単純な問い合わせでもよいが、クエリ処理はUIから分離し、後からDB関数へ置き換えられる形にする。

### 11.3 グラフ要件

- グラフタイトル
- 期間
- 軸名と単位
- 凡例
- データ0件時の表示
- 色だけに依存しない判別
- 数値の一覧または読み上げ可能な代替
- スマートフォン幅でラベルが重ならない

### 11.4 完了条件

- 日・週・月を切り替えられる
- 表示値が元記録の手計算と一致する
- kg/lb表示が設定に従う
- 部位別合計が全体合計と整合する
- 種目を切り替えられる
- 0件でも画面が壊れない
- スマートフォンでグラフが横にはみ出さない

## 14. テスト方針

### 14.1 単体テスト

優先対象：

- kg/lb変換
- ボリューム計算
- ポイント換算
- エサ換算
- 必要経験値計算
- レベルアップ計算
- 日・週・月の期間計算
- 入力検証

境界値を必ず含める。

- 0
- 最小許容値
- 閾値の1未満、ちょうど、1超過
- 小数
- 最大許容値
- 不正値

### 14.2 DB・統合テスト

- 記録保存と報酬付与が両方成功する
- 途中エラー時に両方取り消される
- 二重送信で報酬が重複しない
- 編集時に差分が正しい
- 削除時に差分が正しい
- エサ残高以上を使用できない
- RLSで他ユーザーの操作を拒否する

### 14.3 E2Eテスト

最低限の主要シナリオ：

1. 新規ユーザーが登録する
2. 初期マソ君が表示される
3. 記録画面から今日を選ぶ
4. 種目を選び記録する
5. 記録一覧に表示される
6. エサが増える
7. ホームでエサを与える
8. 経験値が増える
9. 分析グラフに反映される
10. ログアウトする

### 14.4 手動表示確認

- 360px前後のスマートフォン
- 一般的なスマートフォン
- タブレット
- PC
- 長い種目名
- 長いマソ君名
- 記録0件
- 記録多数
- ダークモードを対応するなら両モード

### 14.5 品質ゲート

各フェーズ終了時に実行する。

```text
npm run lint
npx tsc --noEmit
npm run test
npm run build
```

テストスクリプトは導入したテスト環境に合わせて `package.json` へ追加する。

## 15. セキュリティ確認

- すべてのユーザーデータ表でRLSが有効
- Server Actionでも認証ユーザーを再確認
- クライアントから渡された `user_id` を信用しない
- 記録IDだけで更新せず、所有者条件も確認
- サーバー側で入力値を検証
- 秘密鍵をクライアントコードへ含めない
- エラーメッセージへ内部情報を含めない
- 依存パッケージを必要最小限にする
- メモや名前をHTMLとして直接描画しない
- 連打・再送・同時更新を考慮する
- ログへメール、トークン、秘密情報を不用意に出さない

## 21. MVP完成の定義

次のシナリオが本番環境で一貫して成功すれば、MVPの中心機能は完成とみなせる。

1. ユーザーが登録・ログインできる
2. 自分専用のマソ君と設定が作成される
3. 部位と種目を選んでトレーニングを記録できる
4. ボリュームが正しく計算される
5. 記録日と一覧をカレンダーから確認できる
6. 記録に応じてエサまたはポイントを獲得できる
7. エサやりで経験値とレベルが変化する
8. レベルに応じてマソ君の画像が変わる
9. 日・週・月、部位、種目の分析を確認できる
10. 設定したセット数と重量単位が反映される
11. 他ユーザーのデータへアクセスできない
12. スマートフォンとPCで主要操作を完了できる
13. lint、型チェック、テスト、production buildが成功する

この定義に含まれない3D、SNS、AI提案、ランキング、有料プランなどはMVPへ追加せず、公開後のバックログとして管理する。
